# Ограничения

## Настройка фич

- Архитектура рассчитана на программистов, а не на геймдизайнеров: баланс и состав юнитов меняются только в коде.
- Файлы конфигурации не выбраны: это громоздко и негибко, сложная механика всё равно требует кода.
- Следующий шаг: Lua. Геймдизайнер работает через LLM, которая пишет Lua-код в рамках, заданных программистом:
  собирает юнитов из готовых C++-компонентов, задаёт параметры, описывает сценарии и проверки баланса.

## Событийно-компонентный подход, а не ECS

- В условии важно удобство 20 junior-разработчиков, поэтому выбран привычный событийно-компонентный подход: компонент
  хранит данные, а функции `on` рядом с ними отвечают на события. В базовом сценарии junior берёт готовые компоненты
  и думает только об их композиции.
- ECS быстрее: данные одного вида лежат подряд и обрабатываются группами. Но код сложнее читать: поведение юнита
  разнесено по нескольким системам.
- Спецификация требует хода строго в порядке создания юнитов, а это мешает разбить их на группы для эффективного
  хранения и выполнения.
- Позже порядок можно зафиксировать в рамках этапов хода или снять гарантию для части событий, чтобы выполнять их
  группами.

## Рефлексия

- `SW_REFLECT` (Boost.Describe) позволяет обойти поля набора, команды и записи лога, но не убирает дублирование:
  - формат сценария и лога: команды разбираются позиционно, записи печатаются по именам полей C++;
  - биндинги в Lua для автотестов и сценариев геймдизайнеров пришлось бы писать вручную;
  - у полей нет метаданных (диапазоны, значения по умолчанию, описания), поэтому проверки и подсказки тоже дублируются.
- Генерировать формат, биндинги и проверки из одного описания позволила бы, например, рефлексия C++26 с аннотациями
  (`[[=Range{0, 1000}]]`) или собственное решение: описания полей с метаданными или генератор кода.
